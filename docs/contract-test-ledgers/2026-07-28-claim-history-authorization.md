# Claim history authorization

| Invariant | Risk It Prevents | First Test / Proof | Status |
| --- | --- | --- | --- |
| A valid claim marker already present when a new run is created remains historical audit evidence and does not revoke that run. | Reopening or retrying an issue with a prior orchestrator claim permanently blocks before implementation. | `historical claim markers do not revoke a newly claimed run` in `test/v2-run-issue.test.ts` | green |
| A foreign claim marker first observed after the new run is created remains competing authority and blocks before implementation. | Ignoring every foreign claim marker permits overlapping runners to execute against one issue. | `a competing claim marker added during routing revokes the current run` in `test/v2-run-issue.test.ts` | green |
| Every syntactically valid marker for the current run must also have the exact trusted claim body, and exactly one may exist. | A malformed duplicate could coexist with one valid claim and leave authorization ambiguous. | `a malformed duplicate of the current claim marker revokes the run` in `test/v2-run-issue.test.ts` | green |
| Historical authority is bound to the frozen GitHub comment ID as well as its trusted association and exact body. | Deleting a historical comment and reposting identical text after run creation could impersonate frozen history. | `reposting a deleted historical claim under a new comment id revokes the run` in `test/v2-run-issue.test.ts` | green |
| Authorization is freshly observed before every triage launch. | A competing claim could otherwise allow the routing worker to run before the later implementation gate notices it. | `a competing claim observed after claiming blocks before triage launches` in `test/v2-run-issue.test.ts` | green |
| The same pre-triage observation refreshes ordinary comments used as triage facts. | Clarification posted while the claim is established could be omitted from routing. | `triage receives an ordinary comment posted after the initial issue read` in `test/v2-run-issue.test.ts` | green |
| Refreshing comments never changes the frozen issue title, body, URL, state, or labels. | Mutable issue text could otherwise diverge from the frozen acceptance criteria and split routing authority. | `pre-triage comment refresh preserves the frozen issue body` in `test/v2-run-issue.test.ts` | green |
| A pre-upgrade frozen marker without an ID is accepted only when the live GitHub comment was created and last updated no later than the run. | A package upgrade could revoke legitimate active runs, while body-only compatibility would permit post-creation replay. | `a pre-upgrade snapshot without comment ids accepts only a live claim that predates the run` in `test/v2-run-issue.test.ts` | green |
